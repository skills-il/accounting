# התאמת בנק ישראלי

אוטומציה של תהליך התאמת עסקאות בנק ישראליות מול רשומות הנהלת החשבונות שלכם. הסקיל הזה משתמש בספריית הקוד הפתוח `israeli-bank-scrapers` כדי למשוך עסקאות ונותן לכם זרימת עבודה מסודרת להתאמה, זיהוי פערים והפקת דוחות.

## הבהרה משפטית

כלי זה הוא כלי מידע חינמי, הפועל באמצעות מודל בינה מלאכותית. הוא מתאים שורות בנק מול רשומות הנהלת חשבונות ומסביר את כללי ניהול הספרים והמע"מ הנוגעים לעניין. כל תוצריו מופקים באופן אוטומטי על ידי מודל בינה מלאכותית, ללא מעורבות, בדיקה או אישור של יועץ מס או רואה חשבון. התאמה שהוא מפיק אינה התאמה מבוקרת, אינה חוות דעת מס ואינה ייעוץ מקצועי, אלא נייר עבודה כללי בלבד: הוא אינו בוחן את מלוא הכנסותיכם ואת מלוא המסמכים שלכם. מודל בינה מלאכותית עלול לשגות, להשמיט נתונים או להציג מסקנה שגויה.

כל סיווג שהוא עושה, לרבות השאלה אם ניתן לקזז את מס התשומות בהוצאה או אם חשבונית הייתה טעונה מספר הקצאה, הוא טיוטה אוטומטית לצורכי התארגנות אישית ואינו קביעה. האחריות לדיווח ולתשלום המס היא שלכם, החישוב המחייב הוא של רשות המסים, וייצוג מול רשות המסים שמור למי שרשאי לכך לפי דין. הכלי אינו מהווה תחליף לייעוץ המתחשב בנתונים ובצרכים המיוחדים של כל אדם. תנו ליועץ מס או לרואה חשבון לבדוק את ההתאמה לפני שאתם מסתמכים עליה לצורך דיווח. כל שימוש בפלט ובתוצריו הוא באחריותו הבלעדית של המשתמש.


## הוראות

### שלב 1: הגדרת סביבת העבודה

תתקינו את התלויות הנדרשות לסריקת בנקים ועיבוד נתונים.

```bash
npm init -y
npm install israeli-bank-scrapers csv-parse csv-stringify dayjs
```

שדה ה-`engines` של הספרייה דורש Node.js בגרסה 22.22.2 ומעלה (נבדק מול גרסה 6.12.2), אז בדקו קודם `node --version`. הספרייה נארזת כ-CommonJS, כך שקריאות ה-`require` למטה עובדות למרות שה-README שלה מציג `import` של ESM.

אם אתם מתכננים לייבא קובץ במקום לסרוק, שימו לב מה הבנקים בישראל באמת מייצאים. בפועל
הם מציעים הורדה של Excel (xls/xlsx.) ו-CSV; OFX אינו פורמט ייצוא מובנה בבנקים הקמעונאיים
בישראל, אז התייחסו ל-CSV או Excel כמסלול הייבוא המרכזי, ופנו ל-OFX רק אם למשתמש כבר יש
מצרף או תוכנת הנהלת חשבונות שמפיקה אותו:

```bash
# מסלול הייבוא המעשי הוא CSV (חבילת csv-parse כבר הותקנה למעלה)
# אם ההורדה מהבנק היא Excel, בקשו מהמשתמש לשמור אותה כ-CSV באקסל או בגיליונות,
# וכך נמנעים מהוספת מפענח גיליונות נוסף.

# רק אם באמת יש למשתמש קבצי OFX ממצרף
npm install ofx-js
```

הספרייה הראשית מתוחזקת כאן: https://github.com/eshaham/israeli-bank-scrapers

### שלב 2: הגדרת פרטי גישה לבנק

**שדות פרטי הגישה שונים בין הספקים.** אין מבנה אחיד. שימוש בשדות של הפועלים מול לאומי פשוט לא יצליח להתחבר, והתחברויות כושלות חוזרות עלולות לנעול את החשבון בבנקאות המקוונת, אז ודאו את זה לפני ההרצה הראשונה:

| ספק | שדות פרטי הגישה |
|---|---|
| `hapoalim` | `userCode`, `password` |
| `leumi`, `mizrahi`, `otsarHahayal`, `beinleumi`, `massad`, `max`, `visaCal`, `union`, `pagi` | `username`, `password` |
| `behatsdaa`, `beyahadBishvilha` | `id`, `password` |
| `discount`, `mercantile` | `id`, `password`, `num` |
| `isracard` | `id`, `card6Digits`, `password` |
| `amex` | `id`, `card6Digits`, `password` |
| `yahav` | `username`, `nationalID`, `password` |

`oneZero` הוא היוצא מן הכלל: הוא דורש חמישה שדות (`email`, `password`, `otpCodeRetriever`, `phoneNumber`, `otpLongTermToken`), ו-`otpCodeRetriever` הוא פונקציה ולא מחרוזת, אז אי אפשר לבנות אותו ממשתני סביבה ואסור לתת לו ליפול לברירת המחדל. **אל תנחשו מבנה לספק שאינו בטבלה**: התחברות במבנה שגוי נכשלת ונספרת לקראת נעילת החשבון, אז תיפלו בשגיאה במקום לנחש. המקור המחייב הוא מפת `SCRAPERS` בקובץ `src/definitions.ts` של הספרייה, ולא נוסח ה-README, שעדיין כותב `username` לאמקס.

**קראו את פרטי הגישה ממשתני הסביבה בזמן ריצה.** קובץ JSON אינו מרחיב `${VAR}`: אם תכתבו שם מחרוזת כמו הפלייסהולדר של הסיסמה, הסורק ישלח לבנק את המחרוזת המילולית עצמה, ההתחברות תיכשל וזה ייספר לקראת הנעילה. שמרו בקובץ ההגדרות רק מידע ניתוב שאינו סודי:

```json
{
  "accounts": [
    { "id": "main-business", "companyId": "hapoalim", "credentialsEnvPrefix": "HAPOALIM" }
  ]
}
```

בנו את פרטי הגישה בקוד, מתוך משתני הסביבה, לפי המבנה של הספק. טבלת 18 הספקים המלאה ובונה פרטי הגישה שנכשל בבטחה נמצאים ב-`references/bank-scrapers-credentials.md`. הלולאה שם זורקת שגיאה כששדה חסר, במקום לשלוח לבנק ערך ריק או פלייסהולדר. עצרו אחרי כישלון אימות אחד ואל תנסו שוב בלולאה: בנקים בישראל נועלים גישה מקוונת אחרי מספר קטן של ניסיונות כושלים.

### שלב 2א: מה עולה לכם הסריקה, ולמה כדאי לשקול קודם את המסלול המורשה

לפני שמגדירים משהו, אמרו למשתמש בבירור: הסורק מתחבר עם פרטי הגישה המלאים שלו לבנקאות המקוונת דרך דפדפן, וזה לא אסימון תחום או בר-ביטול; תנאי הבנקים בדרך כלל מגבילים מסירת פרטי גישה וגישה אוטומטית; התחברויות כושלות חוזרות נועלות את החשבון; רק OneZero תומך בגורם אימות שני בספרייה, ולכן בנק שדורש OTP בכל התחברות אי אפשר לסרוק ללא נוכחות אדם; והנתונים שנסרקו רגישים גם במנוחה. לחשבון עסקי, התחילו מקובץ הייצוא של הבנק עצמו, כי ה-README לא אומר אם סורק כלשהו מגיע לאתר הבנקאות העסקית. לתהליך עסקי מתמשך, גוף מורשה לפי חוק שירות מידע פיננסי קורא את נתוני החשבון בלי שהמשתמש חושף פרטי גישה בכלל. פירוט, תאריכים וטיפול בנתונים במנוחה: `references/scraping-risk.md`.

מזהים נתמכים, כל 18 החברים ב-enum בשם `CompanyTypes`. העתיקו את ערך ה-camelCase במדויק: ערך בכתיב kebab-case כמו `otsar-hahayal` גורם ל-`createScraper` לזרוק שגיאה, וב-TypeScript `CompanyTypes.otsarHahayal` הופך טעות הקלדה לשגיאת קומפילציה:
- בנקים: `hapoalim`, `leumi`, `discount`, `mercantile`, `mizrahi`, `otsarHahayal`, `beinleumi` (הבינלאומי), `massad`, `union`, `yahav`, `oneZero` (מסומן כניסיוני ב-README)
- חברות אשראי: `isracard`, `amex`, `max` (לשעבר לאומי קארד), `visaCal`
- מועדוני הטבות: `behatsdaa`, `beyahadBishvilha`
- `pagi`: קיים ב-enum אבל חסר ברשימה של ה-README; התייחסו אליו כלא נבדק.

חברות כרטיסי האשראי חשובות כאן לא פחות מהבנקים: שורה אחת בבנק היא בדרך כלל החיוב החודשי המצטבר מישראכרט, מקס, ויזה כאל או אמקס, והתאמה שלה מחייבת למשוך את רשימת העסקאות של אותה חברה ולהתאים את הסכום המצטבר.

### שלב 3: שליפת עסקאות מהבנק

תיצרו סקריפט סריקה שמושך עסקאות לטווח תאריכים שאפשר להגדיר.

```javascript
const { createScraper } = require('israeli-bank-scrapers');

async function fetchTransactions(bankId, credentials, startDate) {
  const scraper = createScraper({
    companyId: bankId,
    startDate: startDate,
    combineInstallments: false,
    showBrowser: false
  });

  const result = await scraper.scrape(credentials);

  if (!result.success) {
    throw new Error(`הסריקה נכשלה: ${result.errorType} - ${result.errorMessage}`);
  }

  return result.accounts.flatMap(account =>
    account.txns.map(txn => ({
      date: txn.date,                     // תאריך ערך
      processedDate: txn.processedDate,   // תאריך רישום: זה המפתח בצד הבנק
      amount: txn.chargedAmount,
      originalAmount: txn.originalAmount,
      originalCurrency: txn.originalCurrency,
      description: txn.description,
      memo: txn.memo || '',
      // הטיפוס של identifier הוא string | number | undefined, ואצל חלק מהספקים
      // הוא מספר. ממירים למחרוזת: בצד הנהלת החשבונות האסמכתא היא מחרוזת,
      // והשוואת === בין מספר למחרוזת תמיד שקרית.
      reference: txn.identifier != null ? String(txn.identifier) : '',
      status: txn.status,                 // 'completed' | 'pending'
      accountNumber: account.accountNumber
    }))
  );
}
```

שני סינונים שחייבים להחיל לפני ההתאמה, אחרת התקופה לעולם לא תתאזן:

```javascript
// 1. רק עסקאות שנרשמו. שורות pending אינן בתוך יתרת הדף.
const posted = txns.filter(t => t.status === 'completed');

// 2. סגירת התקופה. ל-createScraper יש startDate אבל אין endDate, ולכן הסריקה
//    רצה עד היום ותגרור שורות של החודש הבא לתוך תקופה סגורה.
//    התאריכים מגיעים כמחרוזות ISO ב-UTC לחצות בישראל (1 בינואר הוא
//    "...12-31T22:00:00Z"), ולכן משווים את היום בלוח הישראלי כטקסט,
//    כש-periodStart ו-periodEnd הם מחרוזות 'YYYY-MM-DD'.
const ilDay = s => new Date(s).toLocaleDateString('sv-SE', { timeZone: 'Asia/Jerusalem' });
const inPeriod = posted.filter(t => {
  const d = ilDay(t.processedDate || t.date);
  return d >= periodStart && d <= periodEnd;
});
```

הסורק גם לא מגיע רחוק אחורה: בערך שנה ברוב הספקים ושישה חודשים ביהב. לתקופה ישנה יותר, ייבאו במקום זאת את קובץ הייצוא של הבנק (ראו `references/period-close.md`).

### שלב 4: ייבוא רשומות הנהלת חשבונות

תטענו את החשבוניות והקבלות מ-CSV, או תתחברו למערכת הנהלת החשבונות שלכם. מנוע ההתאמה מצפה לרשומות בפורמט מנורמל.

פורמט רשומת חשבונאות צפוי:

| שדה | סוג | תיאור |
|------|------|--------|
| `date` | `YYYY-MM-DD` | תאריך עסקה |
| `amount` | `number` | סכום בש"ח (שלילי להוצאות) |
| `net_amount` | `number` | סכום החשבונית לפני מע"מ, לבדיקת מספר ההקצאה |
| `reference` | `string` | מספר חשבונית/קבלה |
| `vendor` | `string` | שם הספק או מקבל התשלום |
| `category` | `string` | קטגוריה חשבונאית |

כשמייבאים CSV, תטפלו בפורמטים ישראליים:
- סכומי שקלים יכולים להשתמש בפסיק כמפריד עשרוני (1,234.56 או 1.234,56)
- תאריכים יכולים להופיע כ-DD/MM/YYYY (פורמט ישראלי) במקום YYYY-MM-DD
- שמות עסקים בעברית דורשים קידוד UTF-8

### שלב 5: הגדרת כללי התאמה

תגדירו את הכללים שמזווגים שורת בנק עם רשומה חשבונאית, לפי סדר הביטחון הזה:

1. **אסמכתא**: מספר צ'ק, מזהה תנועה או אסמכתא כששני הצדדים נושאים אחד. הכלל הזה ראשון, כדי ששני תשלומים באותו יום ובאותו סכום לא יוצלבו.
2. **מדויק**: אותו תאריך ואותו סכום.
3. **תאריך גמיש**: אותו סכום בחלון תאריכים קצר, בשביל הפרשי תאריך ערך.
4. **סטייה**: אותו תאריך, סכום בטווח של 1.00 ש"ח לשורות שקליות. המרת מטבע צריכה במקום זה טווח באחוזים, כי הפער בין השער היציג לשער של הבנק גדל עם הסכום; את הפער הזה רושמים כהפרש שער.
5. **מקובץ**: שורת בנק אחת שמסלקת כמה רשומות (כולל הודעת זיכוי שקוזזה, או תשלום בניכוי מס במקור), כמה שורות בנק שמסלקות רשומה אחת (תשלומים, תשלום חלקי), וסליקת האשראי.

תחילו אותם מהביטחון הגבוה לנמוך, ואל תתנו לכלל בביטחון נמוך לדרוס התאמה שכלל חזק יותר כבר ביצע. הגדרות הכללים המלאות, הנרמול שדה-אחר-שדה (תיאורים בעברית, פורמטי תאריך, מוסכמות סימן) והמתאימים של המקובץ וסליקת האשראי נמצאים ב-`references/matching-rules.md`.

### שלב 6: הרצת מנוע ההתאמה

תריצו את תהליך ההתאמה ותסווגו את התוצאות לשלוש קטגוריות:
1. **מותאם** - עסקת בנק שמותאמת לרשומה חשבונאית
2. **לא מותאם בבנק** - עסקאות בנק בלי רשומה חשבונאית מתאימה
3. **לא מותאם בהנהלת חשבונות** - רשומות חשבונאיות בלי עסקת בנק מתאימה (הפקדות ממתינות או שגיאות)

קטגוריית "לא מותאם בבנק" מתפצלת לשני מקרים שונים שדורשים טיפול שונה:

מקרה ראשון, חשבונית חסרה: הוצאה או הכנסה עסקית אמיתית שהמשתמש פשוט עוד לא רשם בספרים (חיוב מספק בלי חשבונית רשומה, תשלום מלקוח בלי חשבונית רשומה). את אלה צריך לחקור, המשתמש חייב לאתר או ליצור את המסמך התומך.

  לשני הכיוונים חובות שונות. בחיוב לא מותאם אתם המקבלים, וסעיף 38(א1) הוא שנושך: בלי מספר הקצאה אתם מאבדים את מס התשומות. בזיכוי לא מותאם אתם המוציאים, וסעיף 47(א2) הוא שנושך: מעל אותו סף עוסק מורשה שמוציא את חשבונית המס חייב לבקש מספר הקצאה כשהקונה דורש זאת. וחמור מזה: תקבול בלי חשבונית בספרים עלול להיות מחזור ומס עסקאות שמעולם לא דווחו; אם הדוח למע"מ של אותה תקופה כבר הוגש, זה תיקון לטיפול רואה החשבון ולא רק מסמך ליצור. לפני שקובעים שתקבול מלקוח "חסר", בדקו אם הוא מסלק חשבונית פתוחה בניכוי מס הכנסה במקור: הזיכוי בבנק ועוד אישור הניכוי שווים לחשבונית, אז רושמים את הסכום שנוכה ולא מוציאים חשבונית שנייה. אל תחילו רק את הכלל של צד המקבל על התאמת תקבולים.

מקרה שני, רשומה שמקורה בבנק שלא נרשמה: רשומה שהבנק עצמו יצר ושכלל אין לה חשבונית, כמו עמלות בנק, ריבית, חיובי המחאות חוזרות, עמלות המרת מטבע, ותשלומי הלוואה של הבנק עצמו. חיובי הבנק האלה אינם מסמכים חסרים: רושמים אותם ישירות בספרים כהוצאה או הכנסה מתאימה. חיוב חוזר לצד שלישי (חשמל, טלפון, משכיר עסקי) אינו כזה: המוטב מוציא חשבונית מס, ובלעדיה מס התשומות אובד.

שורה שמסומנת הוראת קבע / הו"ק יכולה להיות חיוב לפי הרשאה לחיוב חשבון או העברה קבועה: הסכום יכול להשתנות, ולכן כלל של "סכום יציב" מפספס רבות מהן, ובחיוב כזה הלקוח רשאי לבטל חיוב מסוים עד 3 ימי עסקים אחרי מועד החיוב (ודאו את הסוג מול הבנק או ברשימת ההרשאות בחשבון לפני שמסתמכים על כך). התאימו שורת החזר לחיוב שהיא מבטלת (`references/period-close.md`).

תסמנו כל רשומת בנק לא מותאמת כאחד משני המקרים האלה לפני הדיווח, כדי שהמשתמש ידע אם לחפש מסמך או פשוט לרשום פקודת יומן.

בנוסף, תסמנו עסקאות חשודות:
- סכומים כפולים באותו תאריך לאותו מוטב
- עסקאות גדולות במיוחד (מעל סף שאפשר להגדיר)
- רישומים בחשבון הבנק בשבת או בחג ישראלי (שישי וראשון הם ימי בנקאות רגילים; תאריך של שורת כרטיס אשראי הוא תאריך הרכישה, אז אל תסמנו אותה)

### שלב 7: בניית גשר ההתאמה

התאמת בנק היא לא רק ספירה של פריטים מותאמים ולא מותאמים, היא חייבת להסביר את הפער בין יתרת הספרים ליתרת הבנק עם גשר מפורש שמתאזן לאפס.

**קודם כול, השיגו את שלוש היתרות.** בלעדיהן אי אפשר לבנות את הגשר, והסורק לא ייתן לכם אותן:
- **יתרת פתיחה ויתרת סגירה בספרים** מגיעות ממערכת הנהלת החשבונות עבור התקופה המתואמת, לא מהבנק.
- **יתרת סגירה בבנק** חייבת להגיע מדף החשבון של סוף התקופה. שימו לב ש-`account.balance` שהספרייה מחזירה הוא היתרה הנוכחית ברגע הסריקה, ולא יתרת הסגירה של תקופה שחלפה, ולכן הוא המספר הלא נכון להתאמה חודשית. בקשו מהמשתמש במפורש את יתרת הסגירה שבדף.

לפני הגישור, הוכיחו שצד הספרים זז כמצופה:

```
יתרת פתיחה בספרים + תקבולים שנרשמו - תשלומים שנרשמו = יתרת סגירה בספרים
```

ואז גשרו מהספרים אל הבנק:

```
יתרת ספרים (סגירה, לפי ספר החשבונות)
  + המחאות שטרם נפרעו: נכתבו ונרשמו, כלומר כבר נוכו בספרים,
    אבל הבנק עוד לא חייב אותן, ולכן יתרת הבנק עדיין גבוהה יותר בסכום הזה
  - הפקדות בדרך: נרשמו כמתקבלות, כלומר כבר נוספו בספרים,
    אבל הבנק עוד לא זיכה אותן, ולכן יתרת הבנק עדיין נמוכה יותר בסכום הזה
  - עמלות בנק שעוד לא נרשמו בספרים: הבנק כבר גבה אותן
  + ריבית בנק שעוד לא נרשמה בספרים: הבנק כבר זיכה אותה
  - שיקים חוזרים ו- + החזרי חיוב לפי הרשאה שהבנק רשם והספרים עוד לא
  +/- עיגולים שנשארו מהתאמות בטווח סטייה, והפרשי שער
  = יתרת בנק (סגירה, לפי הדף)
```

במקום לשנן סימנים, בדקו את הכיוון: כל פריט מתאם מיושם על היתרה שעדיין לא משקפת אותו. שיק שכתבתם כבר יצא מהספרים אבל לא מהבנק, ולכן הבנק עדיין מחזיק את הכסף ומראה יתרה גבוהה יותר. הפקדה שרשמתם עוד לא הגיעה לבנק, ולכן הבנק מראה יתרה נמוכה יותר. אם הגשר לא נוחת בדיוק על יתרת הדף, ההפרש עצמו הוא ממצא: אל תכריחו אותו להתאזן.

שני פריטי התזמון שלמעלה הם הפרשי מועד ולא טעויות (הספרים נכונים, הבנק עוד לא עדכן). עמלות וריבית שלא נרשמו הן ההפך: הבנק נכון והספרים צריכים פקודת יומן (ראו שלב 6).

קודם כול שאלו לאיזה חשבון נרשמים השיקים הדחויים: אם ספר החשבונות מחזיק אותם בחשבון נפרד של שיקים לגבייה או שיקים לפירעון ולא בחשבון הבנק, הם בכלל לא פריטי מתאם בהתאמת הבנק. אחרת, רשמו את השיקים הדחויים בשורות נפרדות, שהתקבלו ושניתנו בנפרד ולפי תאריך הפירעון: בניגוד להמחאה רגילה שטרם נפרעה, שיק דחוי נשאר פריט מתאם עד שהתאריך שלו עובר והבנק מחייב אותו, ומתגלגל בין התקופות.

הדוח צריך לכלול:
- **סעיף סיכום**: סה"כ מותאמים, לא מותאמים, ספירות וסכומים בכל צד
- **טבלת עסקאות מותאמות**: רשומת בנק מזווגת עם רשומה חשבונאית
- **עסקאות בנק לא מותאמות**: מפוצלות ל"חשבונית חסרה" ו"רשומה שמקורה בבנק שלא נרשמה", ממוינות לפי סכום בסדר יורד. בפריט של חשבונית חסרה, לרדוף אחרי החשבונית זה לא מספיק: חשבונית מס מעל סף מספר ההקצאה מחייבת `מספר הקצאה` מפלטפורמת רשות המיסים, ובלעדיו סעיף 38(א1) לחוק מע"מ שולל את מס התשומות על ההוצאה. לכן סמנו חיובים כאלה כ"להשיג חשבונית שנושאת מספר הקצאה תקף", ולא רק "למצוא את החשבונית".

  **התאמת בנק היא רטרוספקטיבית, אז תשתמשו בכל טבלת הספים ולא רק בשורה של היום.** הסכומים לפני מע"מ והסף יורד בשלבים: 25,000 ש"ח מ-5 במאי 2024, 20,000 ש"ח מינואר 2025, 10,000 ש"ח מינואר 2026, ו-5,000 ש"ח מיוני 2026. תנועות שתאריכן לפני 5 במאי 2024 קדמו למודל ומעולם לא נדרש להן מספר. תבדקו את הסכום לפני מע"מ של כל חשבונית (ולא של כל שורת בנק, כי חיוב אחד יכול לסלק כמה חשבוניות) מול הסף שהיה בתוקף בתאריך שלה עצמה. השלמת פערים של שנה קודמת היא בדיוק המקום שבו זה משתבש: החלת ה-5,000 של היום על תקופה מ-2025 מייצרת ערימת ממצאי שווא, ודווקא בתקופות הישנות עוסקת רוב ההשלמה.

  שתי מגבלות נוספות. החוק כותב "עולה על", כך שחשבונית בדיוק בגובה הסף אינה בתחולה. וחשבונית בשיעור אפס או חשבונית שכוללת רק עסקאות פטורות אינה טעונה מספר, אז אל תסמנו חיוב לא מותאם שהחשבונית שלו מכסה ייצוא או עסקה פטורה. התאימו מספר הקצאה לפי 9 הספרות הימניות שלו, שזו הצורה שמודפסת על החשבונית. רק חשבונית מס שהוצאה למשתמש תומכת בניכוי; קבלה או חשבון עסקה אינם סוגרים את הפריט. היעדר מספר עולה בניכוי מס התשומות, ומ-1 באוגוסט 2025 גם בניכוי ההוצאה עצמה למס הכנסה (סעיף 32(18) לפקודה). הספק עדיין רשאי לבקש מספר אחרי שהוציא את החשבונית (סעיף 47(א2)(4)), אבל זה לא מאריך את חלון ששת החודשים לניכוי מס התשומות (סעיף 38(א)), אז רדפו אחריו מהר. פירוט ומקורות: `references/vat-and-fx-rules.md`.
- **רשומות חשבונאיות לא מותאמות**: רשומות שצריך לבדוק, כולל המחאות שטרם נפרעו, שיקים דחויים (ברשימה נפרדת, לפי תאריך הפירעון), והפקדות בדרך
- **פריטים חשודים**: רשומות מסומנות שדורשות בדיקה ידנית
- **גשר התאמה**: יתרת ספרים, התאמות ההמחאות שטרם נפרעו / ההפקדות בדרך / העמלות / הריבית, ויתרת הבנק המתקבלת. שני הצדדים חייבים להתאזן להפרש אפס אחרי שכל פריטי המתאם רשומים
- **חתימה וגיול**: מכין, בודק, הדף שאליו ההתאמה קשורה, והגיל של כל פריט פתוח (`references/period-close.md`)

סגרו כל תקופה על גבול תקופת הדיווח למע"מ של המשתמש (חודשית או דו-חודשית לעוסק מורשה; שאלו איזו, ראו `references/vat-and-fx-rules.md`), כך שממצא על מס תשומות יגיע לפני הדוח שהיה מקזז אותו.

התאמה היא מצטברת: היתרה המתואמת בסגירת התקופה הקודמת היא היתרה הפותחת של התקופה הזו, וכל המחאה שטרם נפרעה או הפקדה בדרך שלא נפרעה מתגלגלת לפריטי המתאם של התקופה הבאה עד שהיא נפרעת.

פורמטי פלט:
- CSV לייבוא לתוכנות גיליונות אלקטרוניים
- JSON לעיבוד בקוד
- סיכום קונסולי לבדיקה מהירה

### שלב 8: טיפול בחשבונות מטבע חוץ

כשמתאימים חשבון מטבע חוץ או עסקאות במטבע חוץ, תעריכו את רשומות הספרים לפי השער היציג של בנק ישראל. ציינו במפורש באיזו מוסכמת תאריך השתמשתם, כי שתי מוסכמות שונות נותנות שתי תוצאות שונות: תאריך העסקה להערכת רישום בודד, ותאריך סוף התקופה להערכה מחדש של יתרת המטבע לסוף התקופה. כתבו בדוח באיזו מהן בחרתם.

השער מפיל התאמות בלוח השנה הישראלי: ביום שישי יש שער, אבל אין שער בשבת, ביום ראשון, בחגי ישראל ובשאר הימים שברשימה השנתית של בנק ישראל, ובהם השער האחרון שפורסם ממשיך לחול; הוא מתפרסם רק אחר הצהריים (בסביבות הצהריים בימי שישי), ולכן רישום באותו יום לא יכול להשתמש בו בזמן אמת; ואין לו מעמד משפטי משלו. באיזה שער הספרים חייבים להשתמש לצורכי מס זו שאלה לרואה החשבון. פירוט: `references/vat-and-fx-rules.md`. שימו לב שהבנק רושם המרה משלו לפי השער שלו בתאריך הסליקה, וזה יהיה שונה מהשער היציג. הפער בין השער היציג לשער ההמרה בפועל של הבנק הוא הפרש שער אמיתי, תרשמו אותו כרווח או הפסד משער חליפין, אל תתייחסו אליו כפער לא מוסבר. תרחיבו בהתאם את סף ההתאמה לעסקאות במטבע חוץ.

### שלב 9: שמירת ההתאמה והמסמכים התומכים בה

את פנקסי החשבונות, הרישומים והמסמכים התומכים הקשורים לניהול העסק (כולל דפי הבנק שמולם ביצעתם את ההתאמה ודוחות ההתאמה עצמם) יש לשמור במשך 7 שנים. חלק מהזרימות האלה מזינות דוח מס שנתי (ראו דוגמה 3), וחלון השמירה נספר מתום שנת המס, או 6 שנים מיום הגשת הדוח, לפי המאוחר מביניהם. תארכבו את דוח ההתאמה של כל תקופה יחד עם דף הבנק והייצוא החשבונאי המותאם שהפיק אותו, כך שאפשר יהיה לשחזר את התיעוד אם רשות המסים תבקש.

## דוגמאות

### דוגמה 1: התאמה חודשית לעסק קטן

המשתמש אומר: "התאם את חשבון העסק שלי בבנק הפועלים לינואר 2026 מול הייצוא מ-QuickBooks."

פעולות:
1. שליפת עסקאות מבנק הפועלים לתאריכים 1-31 בינואר 2026 עם `israeli-bank-scrapers`
2. פענוח קובץ ה-CSV מ-QuickBooks, נרמול תאריכים מ-DD/MM/YYYY ל-YYYY-MM-DD וסכומים לש"ח
3. הרצת כללי התאמה: התאמה מדויקת לפי אסמכתא קודם, ואז התאמה מקורבת לפי תאריך+סכום
4. זיהוי 142 עסקאות מותאמות, 8 עסקאות בנק לא מותאמות, ו-3 רשומות חשבונאיות לא מותאמות

תוצאה: דוח התאמה שמציג שיעור התאמה של 94.7% בצד הבנק (142 מתוך 150 שורות הבנק). תגידו במפורש לפי איזה מכנה חישבתם: מותאמות חלקי שורות הבנק, חלקי הרשומות החשבונאיות, או חלקי כלל הפריטים, נותנות שלושה מספרים שונים, וציטוט אחד מהם בלי לומר איזה מסתיר איפה יושבות החריגות. 8 הרשומות הלא מותאמות בבנק הן משיכות מכספומט בלי רישום בקופה: משיכה היא העברה לקופה הקטנה ולא הוצאה, ולכן היא מותאמת לרישום בספר הקופה ולא לקבלה. 3 הרשומות החשבונאיות הלא מותאמות הן צ'קים שעוד לא נפרעו. הדוח מדגיש חיוב כפול חשוד של 2,450 ש"ח אצל אותו ספק באותו תאריך.

### דוגמה 2: התאמת ריבוי בנקים עם כרטיסי אשראי

המשתמש אומר: "אני צריך להתאים גם את חשבון העו"ש שלי בלאומי וגם את כרטיס האשראי מקס מול מערכת הנהלת החשבונות שלי לרבעון 4 של 2025."

פעולות:
1. שליפת עסקאות מבנק לאומי (אוקטובר-דצמבר 2025) ומכרטיס אשראי מקס לאותה תקופה
2. טעינת רשומות חשבונאיות מייצוא CSV מסונן לרבעון 4
3. הרצת התאמה בנפרד לכל חשבון, ואז הפקת סיכום משולב
4. התאמת שורות תשלומים בכרטיס האשראי לרשומת הרכישה האחת בספרים

תוצאה: דוח התאמה משולב שמכסה את שני החשבונות. עו"ש לאומי מציג שיעור התאמה של 97% עם 12 פריטים לא מותאמים. כרטיס אשראי מקס מציג שיעור התאמה של 91%. 4 רכישות התשלומים נשארות רשומות רכישה בודדות (ההוצאה ומס התשומות שלה נוצרים בחשבונית הרכישה); כל שורת תשלום חודשית מותאמת אליהן כסילוק חלקי, והתשלומים שנופלים ב-2026 נשארים התחייבות פתוחה בכרטיס ולא פריט לא מותאם. הפרש שיורי: 127.50 ש"ח, שמקורו בפער בין השער היציג לשער ההמרה של הבנק עצמו בסליקה. זה הפרש שער ולא סטיית עיגול, ולכן הוא לא נשאר בשארית: רושמים אותו כרווח או הפסד משער חליפין, ואז הגשר מתאזן לאפס. התאמה שמסתיימת בשארית שאינה אפס עוד לא הסתיימה.

### דוגמה 3: זיהוי חשבוניות חסרות לפני הגשת דוח מס

המשתמש אומר: "אני צריך למצוא את כל עסקאות הבנק מ-2025 שאין להן חשבוניות תואמות לפני הגשת דוח המס השנתי."

פעולות:
1. שליפת חודשי 2025 שעדיין בתוך החלון של סורק דיסקונט (שנה פחות יום), וייבוא קובץ הייצוא של הבנק לחודשים המוקדמים יותר
2. טעינת מרשם החשבוניות המלא מייצוא מערכת הנהלת החשבונות
3. התאמה של כל העסקאות, עם דגש על זיהוי חיובי בנק לא מותאמים (הוצאות בלי חשבוניות)
4. קיבוץ של עסקאות לא מותאמות לפי ספק וקטגוריה

תוצאה: נמצאו 34 עסקאות הוצאה בסך 18,200 ש"ח בלי חשבוניות תואמות. הפערים הגדולים הם: ציוד משרדי מספק שחייב במזומן (6 עסקאות, 3,400 ש"ח), מנויי תוכנה שחויבו בדולר והומרו (8 עסקאות, 5,100 ש"ח), וחיובי חניה/כבישי אגרה (20 עסקאות קטנות, 9,700 ש"ח). מתקבלת רשימה מתועדפת לרואה החשבון לאיתור או יצירת חשבוניות חסרות, עם סימון שמס התשומות על חשבונית מ-2025 שעברו ממנה יותר משישה חודשים כבר לא ניתן לניכוי בדרך הרגילה.

## שרתי MCP מומלצים

שרתי ה-MCP האלה יכולים לספק את נתוני העסקאות שהסקיל הזה מתאים, כך שהסוכן לא צריך לכתוב ולהריץ סקריפט סריקה ישירות:

- **`israeli-bank`**, **`il-bank`**, **`asher`** - שרתי MCP שעוטפים את ספריית `israeli-bank-scrapers` וחושפים שליפת עסקאות בנק וכרטיסי אשראי ככלי MCP. השתמשו באחד מהם כדי למשוך את צד הבנק של ההתאמה (לאומי, הפועלים, דיסקונט, מזרחי טפחות, וחברות האשראי) במקום לתחזק סקריפט סריקה מקומי.
- **`boi-exchange`** - שרת MCP לשערים יציגים של בנק ישראל. השתמשו בו במקרה התאמת מטבע החוץ בשלב 8 כדי להעריך רשומות ספרים במטבע חוץ לפי השער היציג הנכון.

אם יש שרת MCP זמין, תעדיפו אותו לשליפת עסקאות, ותיפלו חזרה לסקריפט של ספריית `israeli-bank-scrapers` (שלב 3) כשאין שרת MCP מוגדר.

## מלכודות נפוצות

- עמלת בנק, זיכוי ריבית או חיוב המחאה חוזרת שמופיעים בדף הבנק אבל לא בספרים אינם חשבונית חסרה. זו רשומה שמקורה בבנק שצריך לרשום בספרים עם פקודת יומן, לא לחקור כמסמך אבוד. סוכנים עלולים לבזבז את זמן המשתמש בחיפוש חשבונית שמעולם לא הייתה קיימת.
- לכל בנק ישראלי (לאומי, הפועלים, דיסקונט, מזרחי טפחות, בינלאומי) יש פורמט ייצוא תנועות שונה. סוכנים עלולים להניח מבנה CSV אחיד בין כל הבנקים.
- תאריכי תנועות בנקאיות בישראל הם בפורמט DD/MM/YYYY. סוכנים עלולים לפרסר תאריכים כ-MM/DD/YYYY ולהחליף בשקט בין יום לחודש.
- פירעון המחאות לא עובד כמו "ציפה של 1-3 ימים", וההבדל חשוב להתאמה. שיק שהופקד מזוכה כבר ביום הסליקה, אבל הזיכוי זמני והוא נעשה סופי רק אחרי שלושה ימי עסקים נוספים, שבמהלכם הבנק הנמשך עדיין יכול לסרב לו. כלומר הזיכוי מופיע בדף מיד ואחר כך יכול להתבטל. המשמעות המעשית: שיק חוזר יכול לבטל הפקדה שכבר התאמתם בתקופה קודמת, וזה מחייב לפתוח מחדש את ההתאמה, לחייב חזרה את הלקוח, ולהתייחס לביטול כאל יותר משורת עמלה.
- הבנקים בישראל עובדים מראשון עד שישי, ויום שישי הוא יום בנקאות מקוצר שמסתיים ב-14:00. רק הבורסה בתל אביב עברה למסחר בשני עד שישי (מ-5 בינואר 2026). סוכנים עלולים להתייחס לתנועה מיום שישי או ראשון כחריגה של סוף שבוע, או להחיל את שבוע הבורסה על שורות בנק.
- סליקת כרטיסי אשראי בישראל מגיעה כחיוב מרוכז מחברות האשראי (ישראכרט, כאל, מקס), לא כתנועות בודדות. סוכנים עלולים לנסות להתאים רכישות בודדות מול דפי בנק במקום להתאים את סכום הסליקה הכולל.

## פתרון בעיות

### שגיאה: "Scrape failed: INVALID_PASSWORD"
סיבה: פרטי הגישה לבנק שגויים, פגו תוקף, או שהחשבון דורש איפוס סיסמה. חלק מהבנקים הישראליים מחייבים החלפת סיסמה תקופתית.
פתרון: תאמתו את פרטי הגישה על ידי כניסה ידנית לאתר הבנק. אם הסיסמה שונתה לאחרונה, תעדכנו את משתני הסביבה. רק OneZero תומך בגורם אימות שני בספרייה, ולכן בנק שדורש OTP בכל התחברות אי אפשר לסרוק ללא נוכחות אדם. אם `errorType` הוא `ACCOUNT_BLOCKED` או `CHANGE_PASSWORD`, עצרו ובקשו מהמשתמש לטפל בזה באתר הבנק עצמו; לעולם אל תנסו שוב.

### שגיאה: "No transactions found for the specified date range"
סיבה: טווח התאריכים יכול להיות צר מדי, יכול להיות שאין פעילות בחשבון, או שסורק הבנק דורש פורמט תאריך שונה.
פתרון: תרחיבו את טווח התאריכים ותוודאו ש-`startDate` הוא אובייקט Date תקף ב-JavaScript. תבדקו שיש עסקאות בחשבון הבנק בתקופה שציינתם, על ידי כניסה לאתר הבנק. חלק מהסורקים מחזירים עסקאות מתאריך ההתחלה ועד היום, לא עד תאריך סיום מוגדר.

### שגיאה: "CSV parsing failed: unexpected character at position N"
סיבה: תוכנות הנהלת חשבונות ישראליות פעמים רבות מייצאות CSV בקידוד Windows-1255 (עברית) או כוללות סמני BOM שמפריעים למפענחי UTF-8.
פתרון: תמירו את הקובץ ל-UTF-8 לפני הפענוח: `iconv -f WINDOWS-1255 -t UTF-8 input.csv > output.csv`. כחלופה, תציינו את הקידוד באפשרויות מפענח ה-CSV. גם תבדקו אם יש מפרידי נקודה-פסיק (נפוץ בייצוא Excel ישראלי) במקום פסיקים.

### שגיאה: "Amount mismatch: bank shows -X but accounting shows -Y"
סיבה: הפרשי עיגול בהמרת מטבע, חישובי מע"מ, או פיצול תשלומים יכולים לגרום לפערים קטנים בין סכומי הבנק לרשומות החשבונאיות.
פתרון: תגדירו את סף סטיית ההתאמה. לסכומי שקלים, סטייה של 1.00 ש"ח מטפלת ברוב מקרי העיגול, וההפרשים שהיא בולעת שייכים לשורת עיגול בגשר. להמרת מטבע השתמשו בטווח באחוזים ורשמו את הפער כהפרש שער. אם הפערים שיטתיים, תבדקו אם המע"מ כלול בסכומי הבנק ולא ברשומות החשבונאיות. תשתמשו בשיעור שהיה בתוקף בתאריך התנועה ולא בשיעור של היום: המע"מ הוא 18% מ-1 בינואר 2025 והיה 17% לפני כן. התאמה של תקופה מ-2024 מול 18% מסמנת כל זוג נכון כאי-התאמה, כי חתימת הברוטו-נטו שם היא 17/117 (14.53%) ולא 18/118 (15.25%).
